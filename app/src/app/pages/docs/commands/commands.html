Commands

A command is a message WBSKT sends to a client, like switching a relay on. You can send one from the console, from the API, or from a workflow's Send to client step. A command to a client that is offline waits until it comes back.

For nowThe console sends only to a client that is online, and doesn't list or cancel waiting commands. Queueing for an offline client works through the API and from workflows.

Send one

Open the client and use Send command. If the client declared its commands (see capabilities), pick one and fill in the form. Otherwise switch to JSON, type a command type like relay.set, and write the payload.

The payload arrives on the board as the JSON you wrote, so {"on": true} arrives as an object, not as text. Text that isn't JSON, like lights on, arrives as a JSON string.

What happens to it

Each command gets an ID, and the client's activity shows it move through these steps:

StepMeans
SentThe client was connected and the command is on its way.
QueuedThe client is offline. The command waits for it.
DeliveredWBSKT wrote it to the client's connection.
AcknowledgedShown as Acked in the console. The client confirmed it arrived. The libraries do this for you, before your code acts on it.
FailedIt couldn't be delivered, or it expired first. The reason is shown.
CancelledSomeone cancelled it while it was waiting.

An acknowledgement means the command arrived, not that it worked. If the outcome matters, have the board send a message back, like relay.state, and react to that.

Commands for an offline client

A registered client that is offline gets its commands later. They wait in its queue and are delivered oldest first as soon as it connects. If it drops before a command is delivered, the command goes back in the queue.

  • A command waits at most 24 hours. You can give it an earlier expiry when you send it.
  • A client can have up to 100 commands waiting. Past that, new ones are refused until some are delivered or cancelled.
  • The API lists what is waiting and cancels any of it (below).
  • A command that expires, or whose client is revoked or deleted while it waits, ends as Failed with the reason.

The expiry travels with the command. A board that receives one after its expiry, say from its own late-arriving connection, refuses it instead of acting on it, and that shows as Failed too. Clients that are pending, rejected or revoked don't get a queue: commands to them are refused.

WorkflowsA Send to client step's command expires when the step stops waiting for its answer: its ack timeout, 30 seconds unless you set it. So an offline board doesn't act on an old command after the workflow gave up on it. See Send to client.

Templates

Save a command you send often as a template: a name, a type and a payload. You can save one straight from a message in a client's Activity. A template is either for the whole workspace or pinned to one policy. A client's Templates menu shows the workspace's templates and those of its own policy, and the policy page lists the ones pinned to it. A workspace can hold 200, each with its own name.

Firmware updates

A client whose library can update its own firmware says so when it connects (the ESP32 library can). You start an update through the API, with a link to the new image (it must be https), its SHA-256 and optionally the version; the console doesn't have a button for it yet. WBSKT sends the client a link, not the image.

The client reports how it goes: accepted, downloading (with progress when it can), and installed with the new version once the new firmware connects, or rejected or failed with the reason. While it restarts it shows as updating. If the new firmware can't reach WBSKT, the board goes back to its previous one.

  • An update is a command: it waits for an offline client and always expires, after 24 hours unless you say sooner.
  • Sending a newer update cancels any older one still waiting, so the board never installs an outdated image.
  • The link is visible to anyone who can read the client. Use a link that expires, not one with a long-lived key in it.

What happens when…

I send a command to an offline board
It is queued and the answer says so, with when it expires. It is delivered the moment the board connects, before newer commands.
The board comes back after the command expired
It never gets it. The command ended as Failed when it expired: "The command expired before the client came back."
The board drops in the middle of receiving it
A command not delivered goes back in the queue. One that was delivered but not acknowledged is not sent again, so a board never acts twice on one command.
A workflow sends to a board that is offline
With Wait for acknowledgement on, the step waits for the board until its ack timeout, then leaves by timeout. With it off, the command is queued and the step carries on at once. A full queue or a client that isn't registered leaves by failed when waiting, and fails the step with COMMAND_NOT_SENT when not.
I send to a client in another workspace
It reads as not found. A command can only reach a client in the workspace it was sent from.
I ping an offline board
Refused with CLIENT_OFFLINE. Pings are never queued.

On the wire

  • A command reaches the client as { type, payload, commandId, expiresAt }. The client answers sys.ack { commandId } on arrival, or sys.ack { commandId, type, refused: "expired" } when it came too late. See the client protocol.
  • Acks for commands sent with an ID never count against the client's message budget.
  • Firmware updates use sys.ota.update, the one reserved type sent as a command, and progress comes back as sys.ota.status.
  • Every route a command can take, the console, the API, a firmware update or a workflow, goes through one sender that checks the client belongs to the sender's workspace first.
  • A gateway silent for 75 seconds has commands for its clients queued rather than sent, and they go out as soon as it is heard from again.
