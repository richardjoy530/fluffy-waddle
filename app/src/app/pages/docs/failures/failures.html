Retries and failures

Steps that reach outside WBSKT can fail: a URL times out, a chat service is down, a board doesn't answer. This page covers how a step tries again, what the run does when it still fails, how split paths fail together, and what happens when a run runs out of credits.

Trying again

Every action step has a Try again setting. A new step starts with it on: 3 tries, waiting 2 seconds, then 4, with up to 20% random spread, never more than a minute.

Try againWaits between tries
OffNo second try.
Same waitThe first wait every time: 5 s, 5 s, 5 s.
Growing waitThe first wait times the try: 5 s, 10 s, 15 s.
Doubling waitTwice as long each time: 5 s, 10 s, 20 s.
  • Tries counts the first one, from 1 to 20. Longest wait caps any single wait. Jitter spreads the waits at random, so many runs failing together don't all try again at the same instant.
  • Only temporary errors are tried again, like a timeout or a 5xx answer. A 4xx answer or a missing setting fails at once, because trying again would get the same answer.
  • Only retry on narrows it further to the error codes you list. Others fail straight away.
  • Each try costs the step's credits again.
  • A wait of 5 seconds or more is kept on the server, not in memory, so a retry survives WBSKT restarting.

When a step still fails

Once its tries are used up, the step's When it still fails setting decides what happens next:

ChoiceWhat happens
Fail this path (default)This path ends as failed. Other paths of the run carry on.
Continue down “error”The step gets an error output, and the run carries on from it. Use it to send a fallback alert.
Treat it as doneThe run carries on from the step's normal output, as if it had worked.
Fail the whole runEvery path stops, and any workflow it started with Run workflow is cancelled.
Jump to another stepThe run carries on from the step you pick.

Whenever the run carries on after a failure, the next steps can read what went wrong as {{lastError.errorCode}} and {{lastError.message}}.

To stop a run on purpose, with your own reason, use the Fail run step.

How a run ends

A run's final status comes from its paths:

Its pathsThe run
All succeededSucceeded
Some failed, some succeededPartly failed
All failed, or a step failed the whole runFailed
Someone cancelled itCancelled
It spent its credit budgetOut of credits

Turn on Fail the run when a path fails in the workflow's settings to stop everything on the first failed path instead of letting the others finish. See run statuses.

Split paths and failures

Split into paths and For each, in parallel start several paths. Wait for paths brings them back together: when all have arrived, when the first has, or when a number of them have.

  • A path that fails still arrives, counted as a failure. The step after the join can read how many succeeded and failed, as joinSucceeded and joinFailed, and decide what to do.
  • A path that ends before it reaches the join, at an End step or an output with nothing after it, never arrives. Waiting for all, the join can't be met, so the run fails with JOIN_BRANCH_ENDED. Waiting for the first or for a number, the join carries on without it, and fails only once too few paths are left to meet it.
  • Exactly one path carries on after the join. The others end there.
  • Splitting without a join is fine for fire-and-forget: each path just runs to its end. But either every path of a split reaches the same join or none does.

Running out of credits

A run spends credits as it goes: 1 to start, then each step's price before it runs. Three limits can stop it, and the step that hits one fails with a code that says which:

CodeThe limitRaise it in
OUT_OF_CREDITS_RUN_BUDGETThis run's budget (10,000 unless the workflow sets another).The workflow's Credit limit per run.
PLAN_CREDIT_LIMIT_REACHEDThe account's credits for the month, with any credit packs.Your plan, or a credit pack. See billing.
WORKSPACE_CREDIT_CAP_REACHEDThe workspace's own monthly cap.The workspace's usage settings.

The run is cancelled and ends Out of credits. Steps already done stay done. When the month or the workspace cap is used up, new runs are refused as well, not queued.

What happens when…

A URL answers 503 three times
With the default Try again, the step tries 3 times over about 6 seconds, then fails, and the path follows When it still fails.
A URL answers 404
It fails on the first try. A 4xx isn't temporary, so it isn't tried again.
WBSKT restarts while a step waits to try again
A wait of 5 seconds or more is kept on the server and carries on after the restart. A shorter one is held in memory, so the step may start its tries over.
One of three split paths fails and the join waits for all
The join is met when the other two arrive, with joinFailed = 1. The run ends Partly failed unless a later step fails it, or Fail the run when a path fails is on, which stops it at the first failure.
A step jumps back to an earlier step on failure
That is allowed, so a run can go round again. Each pass costs credits, so a loop that never succeeds ends when the run's credit budget does.
A run is left with nothing it can do
A run with no path running and nothing waiting is ended from its paths when the engine next starts, or after 30 minutes at most.
The parent of a Run workflow step fails
The run it started is cancelled too.

Rules and API

Retry policy

An action node's retry:

FieldMeaning
strategyConstant (Same wait), Linear (Growing wait: initial × attempt), Exponential (Doubling wait: initial × factorattempt−1).
initialDelayThe first wait. Not negative.
factorGrowth for Exponential, default 2, above 0.
maxDelayThe cap, applied after jitter. At least initialDelay.
maxAttemptsTries in all, 1 to 20.
jitterPctRandom spread, 0 to 100 percent either way.
retryOnError codes or exception types to retry. Empty means any retryable failure.

Each attempt is journaled as NodeRetrying in the run's history.

onFailure

outcome is FailBranch (the default), FailRun, ContinueOnError, ContinueAsSucceeded or JumpToNode with targetNodeId. Compensate is refused at publish. The continuing outcomes write lastError (errorCode, message). The workflow's failFast: true fails the run on the first failed path.

Joins

mode is All, Any or Quorum with quorumCount (at least 1, and no more than a split's path count). A parallel for-each over fewer items than quorumCount waits for all of them. When the deciding arrival is a failure, a fresh path carries on past the join. Joins nest: a split inside a path has its own join.
