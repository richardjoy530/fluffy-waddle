Runs

Each time a trigger fires, the workflow starts a run. The run follows the steps, can split into several paths, can wait for hours or days, and ends with a status that says how it went. Every step it took is kept so you can see exactly what happened.

Run statuses

StatusMeans
RunningAt least one path is still going. A run whose every path is parked on a wait shows as Waiting, with what it waits for and when that ends.
SucceededEvery path finished.
Partly failedSome paths failed and others finished.
FailedEvery path failed, or a step failed the whole run.
CancelledSomeone or something stopped it: you, a newer run replacing it, the workflow being deleted.
Out of creditsIt ran out of credits: its own credit limit, the workspace's monthly cap, or the account's month.

While a run is being stopped it reads Cancelling or Failing for a moment. A run cancelled while some of its paths had already finished ends Partly failed, so the work that was done isn't hidden.

Paths

A run starts as one path. Split into paths and For each, in parallel start more, each with its own copy of the run's data, and Wait for paths brings them back together. A path is going, waiting, finished, failed or cancelled; the run ends when its last path does.

Waiting

A Wait, Wait for signal, Wait for a call, Run workflow, or a Send to client that waits for an acknowledgement parks its path. A parked path costs nothing, takes no space in the engine and survives restarts, so waiting a week is as cheap as waiting a second. When the wait has a time limit, the path leaves by timeout once it passes.

The Runs tab

Each workflow's Runs tab shows the last 30 days: how many runs, how many succeeded, the typical and slowest durations, and the errors that actually happen. Below that is the list, newest first, filterable by outcome. Each row says what started it, how many credits it used, and where it ended or failed. All runs in the explorer lists runs across the workspace.

Runs are numbered per workflow, #1, #2, across every version, and a number is never reused.

Open a run to see it drawn on the workflow as it was at that version, with every step it took marked. Pick a step to see what it did: when, how long, how many tries, the credits it cost, its settings, and its error if it failed. A step waiting for a signal lets you send that signal by hand.

Cancelling a run

Cancel run stops a running run. Paths that are waiting stop at once; a path in the middle of a step finishes that step and stops before the next. Runs it started with Run workflow are cancelled too. It takes a moment, so the run reads Cancelling first.

Test runs

A test run runs a workflow once, now, with data you give it, whatever its trigger. You choose:

  • What to run: your draft, even one never published, or the live version. A copy is taken when it starts, so editing the draft meanwhile doesn't change it.
  • Which trigger, when there is more than one, and the data it starts with, in that trigger's own shape: a client message, a webhook body, a schedule's time.

Test runs are real. Commands reach boards, messages are sent, shared variables change, and credits are spent. They are marked Test, numbered with the other runs, and left out of the stats. A workflow can have one test run going at a time. They work on a disabled workflow too, but not a deprecated one.

For nowThe console's Test run button starts an ordinary run of the published version through its Run by hand trigger, so it needs that trigger and an enabled workflow, and it counts in the stats. Test runs as described here are in the API and coming to the console.

How long runs are kept

A finished run is kept, with every step, for your plan's run history: 7 days on Free, 14 on Maker, 30 on Pro and Team, 90 on Business. Runs still going are never removed.

What happens when…

WBSKT restarts in the middle of a run
Paths that were running start again from the step they were on; one whose step had already been carried out picks up its saved result instead of doing it twice. Waiting paths keep waiting, and timers that came due while it was down fire when it's back.
A run is left with nothing it can do
A run that is still open after 30 minutes with no path going and nothing waiting is closed from what its paths did, so it never hangs forever.
A path is waiting and its wait is lost
It fails with BOOKMARK_LOST within about 10 to 15 minutes rather than waiting forever.
I cancel a run that already finished
Refused with RUN_NOT_CANCELLABLE.
Too many runs are going at once
Your plan sets how many runs can be going at once across all your workspaces: 20 on Free, 100 on Maker, 200 on Pro and above. Past that, new runs are refused, and the refusal is recorded in the audit log, at most once a minute per workflow. Runs started by another run, replays from a queue and replacements are let through, so work already accepted isn't stranded.
I start a test run while one is going
Refused with TEST_RUN_ACTIVE, which names the one going.
In depth

Rules and API

Endpoints

Under /api/v1/workspaces/{workspaceRef}. Reading needs workflows.read; starting, cancelling and signalling need workflows.execute, and a test run also workflows.create.

CallDoes
GET runs, GET workflows/{workflowRef}/runsLists runs, newest first. Filters: status (including Waiting) and isTest. Each row has number, trigger, creditsUsed, failedAt, endedAt, currentStep and, while waiting, waiting.
GET workflows/{workflowRef}/statsOutcome counts, durations (p50, p95, max), success rate, error codes, slowest steps, and a row per day.
GET runs/{runRef}, /history, /definitionThe run with its paths; its history, oldest first; the definition it ran.
POST workflows/{workflowRef}/runsStarts a run through a Run by hand trigger: { triggerNodeId, payload, idempotencyKey }.
POST workflows/{workflowRef}/test-runs{ source: "draft" | "live", payload, triggerNodeId }. Answers { runRefId }.
POST runs/{runRef}/cancelAnswers 202; the run reads Cancelling, then Cancelled.
POST runs/{runRef}/signals/{signalName}Sends a signal to a waiting run.

Starting by hand: the answers

AnswerMeans
200Started, or a retry with the same idempotency key, which returns the original run.
202Queued behind a run with the same correlation key.
409Skipped by the concurrency policy, no Run by hand trigger, WORKFLOW_DISABLED, WORKFLOW_DEPRECATED, PLAN_RUN_LIMIT_REACHED, PLAN_CREDIT_LIMIT_REACHED or WORKSPACE_CREDIT_CAP_REACHED.
503WORKSPACE_BUSY: too many runs starting in the workspace at once. Send it again.

A test run answers TEST_RUN_TRIGGER_REQUIRED (400) when the workflow has several triggers and none was named, TEST_RUN_NO_TRIGGER (400) when it has none, TEST_RUN_TRIGGER_NOT_FOUND for one it doesn't have, and WORKFLOW_VALIDATION_FAILED for a definition with errors.

History entries

A run's history records RunStarted, RunFinalized, RunCancellationRequested, RunFailureRequested; per path BranchStarted, BranchResumed, BranchRecovered, BranchParked, BranchCompleted, BranchFailed, BranchCancelled; per step NodeStarted, NodeCompleted, NodeFailed, NodeRetrying; and joins JoinContinuationSpawned, JoinAbandoned. Warnings that don't stop a run are recorded too: TemplateValueMissing, BranchStatePathMissing, BranchStateLarge (over 80% of the 256 KB limit), CreditBudgetLow (past 80% of the run's limit), CounterStepTruncated, CounterReset, WebhookJsonUnparsable.

History never holds the trigger's body or a step's internal error; an unexpected failure shows as EXECUTOR_CRASH with a fixed message, and the detail goes to WBSKT's own logs.
